# 프로젝트 총정리 — 트랜잭션 & 동시성 실전 학습

이커머스/뱅킹 도메인 이직 준비를 위해 18개 챕터를 "버그 있는 코드 → 테스트로 재현 → 수정 → 로그 기록"의 원칙으로 진행한 전체 과정 요약. 각 챕터의 상세 코드/시행착오는 `docs/LOG000`~`LOG018`에 있고, 이 문서는 그걸 관통하는 큰 그림과 인터뷰 대비 포인트를 정리한다.

## 챕터별 핵심 요약

### Phase 0 — 세팅 ([`LOG000`](LOG000-project-setup.md))
Spring Boot 4.1.0 + Testcontainers + PostgreSQL. 가장 큰 교훈: **라이브러리 버전은 검색 요약이 아니라 원본 레지스트리(Maven Central)로 검증해야 한다** — 존재하지도 않는 `testcontainers 2.0.5`를 믿고 여러 라운드를 허비한 뒤에야 원본 API로 `1.21.3`이 맞다는 걸 확인함.

### Phase 1 — 단일 DB 트랜잭션 기초
1. **[`@Transactional` 없는 이체](LOG001-chapter1.md)** — Spring Data JPA 리포지토리 메서드는 각각 자체 트랜잭션을 가져서, 감싸는 트랜잭션이 없으면 `save()`마다 독립적으로 커밋됨 → 부분 실패 시 롤백 안 됨.
2. **[격리수준](LOG002-chapter2.md)** — `READ_COMMITTED`는 non-repeatable read 발생, `REPEATABLE_READ`는 스냅샷으로 방지. PostgreSQL엔 진짜 `READ_UNCOMMITTED`가 없음(MVCC 구조상 dirty read 자체가 불가능).
3. **[전파 속성](LOG003-chapter3.md)** — `REQUIRED`/`REQUIRES_NEW` 정상 확인. `NESTED`는 JPA/Hibernate 환경(`HibernateJpaDialect.getJdbcConnection()`이 항상 `null`)에서 **근본적으로 지원 안 됨**을 확인.
4. **[Lost Update](LOG004-chapter4.md)** — 10스레드 동시 출금 시 전부 "성공" 처리됐지만 실제로는 1건분만 반영, 9건의 효과가 증발.
5. **[낙관적 락 + 재시도](LOG005-chapter5.md)** — `@Version` + 재시도 루프로 결정론적 결과(정확히 5/5/0) 확보.
6. **[비관적 락 + 데드락](LOG006-chapter6.md)** — `SELECT FOR UPDATE`(Postgres에선 `FOR NO KEY UPDATE`)로 재시도 없이 해결. 반대 방향 동시 이체로 데드락 재현(`CannotAcquireLockException`, SQLState `40P01`), 락 획득 순서 고정으로 해결.

### Phase 2 — 복잡한 비즈니스 케이스
7. **[일일 한도 동시성 제어](LOG007-chapter7.md)** — 낙관적 락(Account)과 비관적 락을 한 트랜잭션에 섞어 쓰면, 재시도 없는 낙관적 락 충돌이 먼저 나서 진짜 버그(한도 우회)를 가려버리는 함정을 겪음. 계좌·한도 둘 다 비관적 락으로 통일해 해결.
8. **[수수료 트랜잭션](LOG008-chapter8.md)** — `REQUIRES_NEW`를 "수수료는 꼭 받아야 하니까"라는 그럴듯한 이유로 오남용 → 이체 실패해도 이미 걷은 수수료는 롤백 안 됨. `REQUIRED`로 수정.
9. **[감사 로그](LOG009-chapter9.md)** — `REQUIRES_NEW`의 **정당한** 사용 사례(챕터 8과 정반대 대비). 실패 사실 자체를 기록해야 하니 메인 트랜잭션과 독립적이어야 함.
10. **[이벤트 발행 타이밍](LOG010-chapter10.md)** — `@TransactionalEventListener(AFTER_COMMIT)`로 롤백된 트랜잭션의 이벤트가 안 나가게 함.

### Phase 3 — 분산 트랜잭션
11. **[2PC 이론과 한계](LOG011-chapter11.md)** — 블로킹 문제, 코디네이터 SPOF, 이기종 시스템 비호환(XA 미지원)으로 실무에서 거의 안 씀. 코드 없이 개념만 정리.
12. **[SAGA Choreography](LOG012-chapter12.md)** — 각 서비스가 이벤트를 구독해 자기 행동을 스스로 보상. "보상은 자기가 한 일을 자기가 되돌린다"는 원칙.
13. **[SAGA Orchestration](LOG013-chapter13.md)** — 중앙 조정자가 명시적으로 보상 호출. 조정자에 `@Transactional`을 붙이면 안 됨(진짜 SAGA가 아니게 됨). 3단계로 확장하며 "보상 스택" 패턴 도입(성공한 단계만 역순 보상).
14. **[Outbox 패턴](LOG014-chapter14.md)** — 메시지 브로커 직접 발행 대신 로컬 DB `outbox` 테이블에 원자적으로 기록. 릴레이는 이벤트별 개별 트랜잭션으로 처리(배치 전체 트랜잭션은 하나의 실패가 전체를 막는 버그).
15. **[멱등성 설계](LOG015-chapter15.md)** — 재시도로 인한 중복 처리 방지. 멱등성 키 확인·처리·기록을 원자적으로 묶음. 다단계 흐름에서는 `(sagaId, step)` 컬럼 분리로 키를 설계. **Phase 3 종합 정리**(원자성 포기→보상, SAGA의 격리성 문제)가 이 문서에 있음.

### Phase 4 — 운영 관점
16. **[락 경합 모니터링](LOG016-chapter16.md)** — `pg_locks`/`pg_stat_activity`로 블로킹 관계 관찰. 관찰 도구 자체보다, 테스트 코드에서 트랜잭션을 안 감싸면 락이 바로 풀려버리는 실수를 겪음.
17. **[커넥션 풀 고갈](LOG017-chapter17.md)** — HikariCP 풀 크기 초과 시 `CannotCreateTransactionException`. 근본 해법은 풀 증설이 아니라 트랜잭션 보유 시간 단축.
18. **[동시성 테스트 자동화](LOG018-chapter18.md)** — 반복되는 스레드 관리 보일러플레이트를 유틸리티로 추출, `@RepeatedTest`로 반복 검증. "자동화"라는 표현이 실제 내용보다 거창했다는 걸 정직하게 재검토.

## 전체를 관통하는 교훈

**1. Read-Modify-Write 패턴은 언제나 위험하다.**
잔액(챕터 4), 일일 사용량(챕터 7) — 형태는 달라도 "값을 읽고 애플리케이션에서 계산해서 다시 쓰는" 패턴은 항상 같은 종류의 동시성 버그를 만든다. DB가 원자적으로 계산해주지 않는 한(락 또는 원자적 UPDATE) 이 위험은 사라지지 않는다.

**2. `REQUIRED` vs `REQUIRES_NEW`의 판단 기준.**
그 작업이 "메인 작업의 결과에 의존하는 효과"인가(→ `REQUIRED`로 같이 묶기, 챕터 8) 아니면 "메인 작업의 성패 자체를 기록/알리는 관찰자"인가(→ `REQUIRES_NEW`로 분리하기, 챕터 9)로 나뉜다.

**3. 진짜 원자성과 흉내낸 원자성은 다르다.**
2PC(챕터 11)의 진짜 원자성은 분산 환경에서 사실상 못 쓴다. SAGA(챕터 12~13)는 원자성뿐 아니라 격리성도 포기하고 보상으로 흉내낸다 — 중간 상태가 실제로 노출될 수 있다는 게 핵심 차이. Outbox(챕터 14)는 문제 범위를 로컬 DB로 좁혀서 그 부분만 진짜 원자성을 되찾는 전략.

**4. Self-invocation 문제는 어디서나 반복된다.**
같은 클래스 안에서 자기 메서드를 호출하면 Spring AOP 프록시를 안 거쳐 `@Transactional`이 무시된다 — 챕터 3(전파속성), 5(재시도), 13(SAGA 보상), 14(Outbox 릴레이)에서 계속 마주침. 반복될 때마다 "다른 빈으로 분리"가 해법이었다.

**5. 락은 최대한 짧게, 필요한 만큼만.**
챕터 6(데드락)과 17(커넥션 풀 고갈)이 같은 교훈을 다른 각도에서 보여줌 — 락/커넥션을 오래 쥘수록 경합·고갈 위험이 커진다.

**6. 검증 없이 사실을 단정하지 않는다.**
LOG000의 버전 삽질, LOG016의 잘못된 예외 타입 예측 등 — 확신 없는 건 실제로 돌려보고 확인한 뒤에 말하는 습관이 이 프로젝트 전체에서 반복적으로 강조됨.

## 반복해서 마주친 함정 (실무에서도 자주 나올 만한 것들)
- `BigDecimal.equals()`는 scale까지 비교해서 `10000`과 `10000.00`을 다르다고 판단 — `compareTo()`(또는 AssertJ `isEqualByComparingTo`)를 써야 함.
- 낙관적 락과 비관적 락을 한 트랜잭션에 섞어 쓰면, 재시도 없는 낙관적 락이 먼저 실패해서 진짜 원인을 가릴 수 있음(챕터 7).
- Spring 빈 이름은 기본적으로 클래스 단순명 기준이라, 다른 패키지에 같은 이름의 클래스를 두면 충돌함(챕터 13).
- 공유 싱글턴 빈(테스트 간 Spring 컨텍스트 캐싱)은 상태가 테스트 메서드 사이에 누적될 수 있음(챕터 10) — 절대 개수보다 "증가량"으로 검증하는 게 안전.
- `@TransactionalEventListener`는 원래 트랜잭션이 "정리 단계의 불명확한 상태"라 `REQUIRES_NEW`/`NOT_SUPPORTED`만 허용(챕터 12).

## 이직 인터뷰 대비 — 예상 질문 포인트
- **"트랜잭션 전파 속성을 실무에서 어떻게 쓰나요?"** → 챕터 8/9 대비 사례(수수료=`REQUIRED`, 감사로그=`REQUIRES_NEW`)로 답변. 판단 기준(위 교훈 2번)을 먼저 말하고 예시로 뒷받침.
- **"동시성 문제를 어떻게 해결하나요? 낙관적 락과 비관적 락 중 뭘 쓰나요?"** → 챕터 5/6 비교(재시도 필요 여부, 블로킹 여부), 챕터 7에서 겪은 "섞어 쓸 때의 함정"까지 언급하면 깊이가 다르게 보임.
- **"분산 트랜잭션은 어떻게 처리하나요? 2PC를 써봤나요?"** → 2PC의 한계(블로킹 문제)를 설명하고, 왜 SAGA/Outbox로 대체하는지, 그 트레이드오프(원자성/격리성 포기 vs 확장성)를 설명.
- **"멱등성을 어떻게 보장하나요?"** → 챕터 15의 키 설계(확인+처리+기록 원자적 묶음), 다단계 흐름에서의 계층 구조 설계까지.
- **"데드락을 겪어본 적 있나요? 어떻게 해결했나요?"** → 챕터 6의 실제 재현 로그(Postgres의 순환 대기 감지, `CannotAcquireLockException`), 락 순서 고정 해법.
- **"운영 중 DB 병목을 어떻게 진단하나요?"** → 챕터 16(`pg_locks`/`pg_stat_activity`), 챕터 17(커넥션 풀 고갈과 그 근본 원인)로 답변.
