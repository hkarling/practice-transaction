# LOG004 — 챕터 4: 동시성 문제 재현 (잔액 음수, Lost Update)

전체 진행도: [`README.md`](../README.md)

## 목표
챕터 1에서 `@Transactional`로 "부분 실패" 버그는 고쳤지만, **동시에 여러 요청이 같은 계좌를 건드리면 여전히 잔액이 안 맞을 수 있다**는 걸 재현한다. 트랜잭션이 있어도 동시성 문제는 별개.

## 시작 전 짚었던 것
- `Account.withdraw()`의 잔액 체크는 자바 메모리에서 일어남 — 여러 스레드가 동시에 같은 계좌를 조회하면 전부 같은(오래된) 잔액을 보고 각자 "충분하다"고 판단할 수 있음.
- Hibernate의 `UPDATE`는 `SET balance = <계산된 최종값>` 형태라, 여러 트랜잭션이 각자 계산한 값으로 서로 덮어씀 (Lost Update).
- 타이밍에 좌우되는 실험이라 실행마다 정확한 숫자는 다를 수 있음. 이 문제는 챕터 5(낙관적 락)/6(비관적 락)에서 결정론적으로 고친다.

## 구현
`ConcurrentTransferTest` — 잔액 10000인 계좌에서 10개 스레드가 동시에 2000씩 출금 시도. `CountDownLatch` 두 개(`readyLatch`/`startLatch`)로 모든 스레드가 최대한 동시에 출발하도록 강제. 성공 횟수 기준 "이론상 맞아야 할 잔액"과 실제 DB 잔액이 다르다는 걸 assert (`isNotEqualByComparingTo`) — 다르다는 것 자체가 Lost Update의 증거.

## 재현 결과
```
성공한 출금 수: 10, 실패한 출금 수: 0
기대 잔액(성공 횟수 기준): -10000, 실제 잔액: 8000.00
```
가장 극단적인 형태로 재현됨:
- 10개 스레드 **전부 성공** — 아무도 잔액 부족 예외를 안 만남. 전부 거의 동시에 `balance=10000`을 읽어서 각자 독립적으로 통과 판정.
- 각자 계산한 새 잔액이 전부 `10000 - 2000 = 8000`으로 동일 — 같은 시작값에서 같은 금액을 뺐으니 당연히 같음.
- 10번의 커밋이 row lock 때문에 순서대로 일어나긴 하지만, 매번 `SET balance = 8000`으로 덮어쓸 뿐이라 최종 잔액이 8000으로 남음 — **마치 출금이 딱 1번만 일어난 것처럼 보임.** 나머지 9번의 출금 "효과"는 완전히 증발.
- 실무 관점: 고객 10명에게 전부 "출금 성공" 응답을 보냈는데, 실제 원장엔 1번만 반영된 셈 — 최악의 시나리오.

## 시사점

**1. `@Transactional`은 "원자성"만 보장하지 "동시성 안전"을 보장하지 않는다.**
트랜잭션은 "이 작업 안의 모든 변경이 전부 반영되거나 전부 안 되거나"(all-or-nothing)만 약속한다. "다른 트랜잭션과 충돌 안 나게 해준다"는 별개의 문제. 챕터 1에서 `@Transactional`을 붙였을 때 "이제 안전해졌다"고 착각하기 쉬운데, 이번 챕터가 그 착각을 깬다.

**2. ORM/프레임워크 문제가 아니라 "Read-Modify-Write" 패턴 자체의 근본적 문제다.**
Hibernate라서, Spring이라서 생긴 버그가 아니다. "값을 읽고 → 애플리케이션에서 계산하고 → 다시 쓴다"는 패턴은 언어/프레임워크와 무관하게 동시성 하에서 항상 이 위험을 안는다. DB에게 "이 계산 자체를 원자적으로 해달라"고 명시적으로 요청하지 않는 한(락, 혹은 `UPDATE ... SET balance = balance - ?`처럼 DB 레벨 원자 연산), 애플리케이션의 잔액 체크는 무의미해진다.

**3. 실무적 함의 — 이커머스/뱅킹에서 왜 치명적인가.**
10개 요청 전부에게 "출금 성공" 응답을 보냈는데 실제 원장엔 1번만 반영됐다는 건, 고객은 돈을 인출했다고 믿는데 은행 장부는 그걸 모른다는 뜻. 정산 불일치, 고객 클레임, 감사(audit) 실패로 직결된다 — 이 도메인 인터뷰에서 동시성 제어를 자주 물어보는 이유.

**4. 챕터 2(격리수준)와의 연결고리.**
PostgreSQL `SERIALIZABLE` 격리수준(SSI)을 썼다면 커밋 시점에 자동 감지돼 한쪽이 직렬화 실패 예외를 던졌을 가능성이 높다. 그런데 "예외를 받은 쪽이 재시도해야 한다"는 책임은 결국 애플리케이션에 넘어온다 — 이게 챕터 5의 **낙관적 락 + 재시도 전략**과 철학적으로 같은 패턴. 격리수준을 올리는 것과 명시적 락을 쓰는 것, 둘 다 "충돌을 감지하고 재시도한다"는 같은 해법으로 수렴한다는 걸 챕터 5에서 보게 된다.

## 완료 체크리스트

- [x] Lost Update 재현 확인 (10개 전부 성공, 실제 잔액이 이론값과 불일치)

## ADR

**Decision**
- 동시성 버그 재현은 정확한 2-스레드 인터리빙 제어(챕터 2 방식) 대신, N개 스레드를 `CountDownLatch`로 동시 출발시켜 자연스러운 경합을 유도하는 방식을 사용.
- 검증은 "이론상 잔액 ≠ 실제 잔액"이라는 불변조건 위반으로 확인 — 정확한 숫자를 예측하지 않고 불일치 자체를 잡아냄.
- 이 챕터에서는 버그를 고치지 않는다 — 재현까지만, 수정은 챕터 5/6(낙관적/비관적 락)에서.

**Drivers**
- `@Transactional`만으로는 동시성 문제를 못 막는다는 걸 직접 보여주는 게 이번 챕터의 핵심.
- 정확한 스레드 교차 타이밍을 강제로 제어하는 건 복잡도 대비 얻는 게 적음 — N개 동시 실행만으로도 충분히 안정적으로 재현됨.

**Alternatives considered**
- 챕터 2처럼 2-스레드 + 여러 `CountDownLatch`로 정밀 인터리빙 제어 — 기각: `TransferService.transfer()`는 내부에 정지 지점을 넣을 훅이 없어(프로덕션 코드에 테스트 전용 훅을 넣고 싶지 않음), N-스레드 동시 출발 방식이 더 간단하고 충분히 효과적.
- 정확한 성공/실패 개수를 미리 예측해서 assert — 기각: 타이밍에 따라 매번 다를 수 있어 실행마다 실패하는 깨지기 쉬운(flaky) 테스트가 될 위험.

**Consequences**
- 이 테스트는 본질적으로 비결정적(non-deterministic)이다 — 실행할 때마다 정확한 수치는 다를 수 있음. CI에서 안정적으로 쓰려면 챕터 5/6에서 락을 적용한 뒤, "이제는 항상 정확히 5개만 성공하고 잔액이 정확히 0이 된다"는 결정론적 버전으로 교체해야 함.
- `TransferService`에 아직 락 관련 코드가 전혀 없다는 걸 명시적으로 확인함 — 챕터 5/6에서 손댈 지점이 명확해짐.

**Follow-ups**
- 챕터 5: `@Version` 낙관적 락 + 재시도 전략으로 이 테스트를 결정론적으로 통과시키기.
- 챕터 6: `SELECT FOR UPDATE` 비관적 락으로 같은 문제를 다른 방식으로 해결, 데드락 재현까지.
